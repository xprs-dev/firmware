# ESP32 inter-device validation

The full set of tests between two ESP32 XPRS full stations on the bench, so a
regression shows up against a known-good run. ESP-NOW is the WiFi-class local
bearer (xwifi is not shipped; see xwifi-implementation.md for why it does not
fit the C3).

## The two stations (2026-10-23)

| | callsign | board | IP | bearers |
|---|---|---|---|---|
| A | X3SQS6 | esp32c3-mini | 192.168.1.230 | BLE5, ESP-NOW, LAN, Reticulum |
| B | X3SEP2 | tdeck (ESP32-S3) | 192.168.1.231 | BLE5, ESP-NOW, LAN, LoRa, Reticulum |

Both on the same access point (Vodafone-16552C): ESP-NOW rides the station's
channel, so associating to one AP puts both on one channel without guessing,
and the LAN bearer needs the shared subnet. Both dial rns.wisco.network:4242.

How each test is run is below so it can be repeated; the method is HTTP to each
station's own API (`/api/...`), no serial needed once they are on the network.

## Results

### 1. Mutual discovery, per bearer

`GET /api/xprs/history?from=<peer>&limit=200`, tally the `bearer` field (each
record carries the lane it was heard on). Both heard the other directly
(0 hops) on every shared bearer:

| receiver → sender | espnow | ble | lan | rns | lora |
|---|---|---|---|---|---|
| A hears B (X3SEP2) | ✓ 98 | ✓ 97 | ✓ 3 | ✓ 2 | — (A has no LoRa) |
| B hears A (X3SQS6) | ✓ 30 | ✓ 107 | ✓ 2 | ✓ 1 | ✓ 60 (relayed) |

Direct BLE RSSI A↔B −17 / −24 dBm. `/api/xprs/devices` dedups to the strongest
lane (BLE here); the per-record tally above is how the other lanes are seen.

### 2. Message delivery, both directions

`POST /api/xprs/send` with a unique token, then `GET /api/xprs/history` on the
other station. The station airs on every local bearer (`bearers:lan,espnow,ble`
in the response) and the receiver's dedup collapses the copies to the first to
land.

| direction | sent on | arrived via | result |
|---|---|---|---|
| A → B `t:message scope:local` | lan,espnow,ble | lan | ✓ |
| B → A `t:message scope:local` | lan,espnow,ble | espnow | ✓ |
| A → B `t:message d:X3SEP2` (directed 1:1) | lan,espnow,ble | espnow | ✓ |

### 3. Reticulum peer-to-peer through the public hub

`/api/xprs/peers` → `rns`: `up:true hub:true peers:1`, and
`addressed:{tx:1, rx:1, via_hub:1, path_req:1}` — the station learned the peer
from a path request and exchanged an addressed wire through the hub, not over
the LAN. The rns rows in the discovery tally are the same path.

### 4. Reachability under load

One ping/s while all bearers carry traffic (BLE beacons, ESP-NOW, LoRa/Mesh
bridging on B, the hub link):

| station | loss |
|---|---|
| A (C3) | 0 % |
| B (T-Deck) | ~10 % — it is the busier board (LoRa + Meshtastic bridge + BLE) |

## Verdict

ESP-NOW, LAN, BLE5 and Reticulum all carry XPRS between the two ESP32 stations,
in both directions, with the cross-bearer bridge and the §5 dedup working and
directed 1:1 delivery confirmed. The C3 carries the fleet-wide `.bss`
relocation of 2026-10-23 (static RAM 93,344 → 74,264) and ran clean throughout.

## Web chat (the hotspot page), on the C3

The page is the `xprs-dev/webchat` repo's page: `common/xprs_hotspot/chat_page.c`
is generated by `webchat/tool/build.py --c`, and the C3 serves it byte-identical
to the current webchat HEAD (the only difference from a fresh regenerate is the
gzip OS flag; both decompress to the same 79,871-byte page).

Driven on the real C3 from a browser on the LAN (the laptop stays on its own
WiFi, reaches the C3 at its LAN IP, never joins the hotspot); the second party
is the T-Deck, another ESP32 station. Via Chrome DevTools against `http://<C3>/`:

- **Page renders** against the live C3: Chat/Traffic/Devices tabs, Local/
  Regional/Global rooms, the feed, the composer, the archive count. The page
  minted its own browser key (an `X1` person callsign).
- **Incoming:** a `t:message` sent from the T-Deck appears in the page's feed
  (e.g. `bench77794r` from X3SEP2).
- **Outgoing:** a message typed in the composer and sent with Enter is **signed
  by the browser's key** (`sig:` on the wire, per the webchat contract) and
  **reaches the T-Deck over ESP-NOW** (`t:message f:<page key> scope:local
  sig:… m:<token>`), and is archived on the C3 over LAN.

So the station only validates and airs a wire; the page holds the key and signs,
and the round-trip to a second ESP32 works both ways.

## WiFi set by a local non-owner (XPRS.md 11.9.1)

Anyone within local range (BLE / ESP-NOW / LAN) may hand the station a WiFi
network, owner or not, so a station whose router changed is put back on the air
without a cable and without the admin present -- with guards so a stranger
cannot abuse it. Implemented in `cmdset_apply`/`setup_apply` and `wk_tick`
(`common/xprs_app/xprs_app.c`):

- **WiFi only, sealed, signed.** A non-owner's `cmd:set` is accepted only if
  every key is `ssid`/`pass`/`wifi`, the body is sealed in `x:` (no password on
  the air), and the signature verifies against a key the station holds. The
  station learns a stranger's key from its `t:identity` (a sealed command plus
  `k:` plus `sig:` overruns 250 bytes, so `k:`-in-command is not the path). Any
  non-WiFi key from a non-owner is refused.
- **Held, never switched, while a link is up.** A non-owner offer does not move
  the station off a working network. It is held in RAM (`s_wcand`) and tried
  only when the current network is down and every remembered (known-good) one
  has failed; it reaches the persisted list only by then giving an address
  (`wk_note`). Lost on reboot -- nothing a stranger said is kept until it has
  worked. The owner's own set still switches immediately (`trusted`).

Bench-verified on the C3 (X3SQS6, on Vodafone), a non-owner identity (X1GSV2)
airing over the T-Deck onto the C3's local bearers:

| case | result |
|---|---|
| non-owner airs `t:identity`, then a sealed WiFi offer | `set up by X1GSV2: wifi:held ssid:StrangerNet`, `t:result ... code:202 wifi:held` -- accepted, **held** |
| C3's current link throughout | stayed on 192.168.1.230, internet up -- **not switched** |
| non-owner sets a non-WiFi key (`nick:`) | `t:result ... code:403` -- refused, nothing changed |

The tool is `reticulum-dart/tool/xprs_setup_bench.dart` (`identity` then
`--ssid .. --pass .. wifi`); the laptop's own UDP broadcast does not reach the
C3 (the AP isolates clients), so the signed/sealed wires are aired through the
T-Deck's `/api/xprs/send`, which is the real path a nearby device would take.

## Time: the clock ladder, the 15.7 anchor, and what crosses to Meshtastic

Meshtastic users read the T-Deck's messages with the wrong time. A Meshtastic
frame carries no timestamp (header: addresses, id, hops, channel; `Data`:
portnum, bytes, ids), so a reader sees the moment the frame reached *their*
radio -- and the bridge used to mirror the bearers' replays of old XPRS
traffic whenever it had no clock (boot, no WiFi), with its old-news gate
dropping silently when it did. Fixed 2026-10-24 (docs/lora.md "Time";
XPRS.md 11.10's new paragraph; `xst_clock_set` in xprs_station):

| check | result |
|---|---|
| host tests | `test_mt_host.sh` all checks (cases 18-20: no clock, settling, dated/stale); `test_xprs_station_host.sh` 105 checks (the ladder: range, never back, owner over hint, nothing over NTP) |
| boot (serial, reset by esptool) | `clock: ntp set 1792795934 UTC` at 14 s -> `clock: now from ntp -- the next beacon anchors epoch 484` -> `clock: epoch 484 anchored on lan (ntp)` |
| 15.7 anchor on the wire (C3 archive) | `t:observation f:X3SEP2 link:lan peers:1 uptime:0m lifetime:8h lx:… ts:2026-10-23_22:52:20 epoch:484.14 hears:X3SQS6` -- both forms, once |
| `/api/status` | `"time":{"synced":true,…,"source":"ntp"}` |
| a 10-min-old message heard from the C3 | serial `mt: text f505cc -> ffffffff …`, `/api/status` mt `dated:1` -> it crossed with `[23:34] ` in front (local, tz +01:00) |
| a 2-h-old one | no `mt: text`; `stale` counted (24 within ten minutes of boot: the carousel that used to be mirrored) |
| no clock / settling | `no_clock:0 settling:0` here: on this WiFi SNTP wins inside the 20 s settle. The refusal path is the host test's case 18/19, and says so in the log once in fifty |

Two bench messages went onto LongFast, labelled "xprs bench, ignore".
The `mt` counters live in `/api/status` (the `lora` block), not `/api/diag`.
Making the T-Deck a time source for the Meshtastic mesh was looked at and
left: Meshtastic nodes take network time only from a Position claiming a GPS.

## Meshtastic gets the Regional room, and nothing wider

LongFast is one valley's air, shared. Until 2026-10-24 the bridge mirrored
global traffic onto it too (the conversation that travels over Reticulum),
and Meshtastic's channel talk landed in the Global room whenever its sender
had ticked "OK to MQTT". Now only `scope:regional` crosses out, never marked
OK-to-MQTT, each sender with a share of the hour; and everything said on the
channel arrives `scope:regional` (XPRS.md 9.11.3/9.11.5, docs/lora.md "What
crosses"). Bench, T-Deck freshly flashed, three messages aired by the C3 at
once:

| wire from the C3 | T-Deck |
|---|---|
| `scope:regional m:xprs bench regional, ignore` | serial `mt: text 4539f8 -> ffffffff …`, `text_out` 0 → 1: **crossed** |
| no scope (global) `m:xprs bench global, must not cross` | no `mt: text`; `not_regional` counted |
| `scope:PT m:xprs bench country, must not cross` | no `mt: text`; `not_regional` counted |
| `not_regional` over the 50 s | 0 → **18**: our two plus sixteen replays of global traffic that used to be mirrored |
| inbound | a Meshtastic NodeInfo arrived as `t:identity f:MTAEAE5890 … scope:regional nick:7BTM_01-GW-8 … via:X3SEP2` |

Host suites: `test_mt_host.sh` (cases 21-22: regional only, never OK-to-MQTT,
a sender's share of four) and `test_mc_host.sh` all pass. One labelled bench
message went onto LongFast.

## Both boards on the new firmware (2026-10-24)

The C3 (X3SQS6, `c3mini`) and the T-Deck (X3SEP2) were flashed over USB
(`pio run -t upload --upload-port …` for the C3; `tools/flash-chunked.sh … 0x20000`
for the T-Deck -- both boards' `platformio.ini` name stale USB ids). The C3's
boot showed a case the ladder had not named: the chip keeps its clock across a
reset, so `/api/status` said `synced:true` with `source:none` for the first
minute. That clock is as good as it was and nothing this boot can vouch for,
so it is now reported as **`kept`**, and the rule became "nothing but NTP turns
a valid clock back" -- an owner's command no longer winds a kept clock back to
its own `ts:`.

| board | boot |
|---|---|
| T-Deck | `clock: ntp set` at 9 s -> `anchors epoch 486` -> `epoch 486 anchored on lan`; `settling:1` (a heard message inside the 20 s gate) |
| C3 | `source:kept` at 7 s -> `now from ntp` at 68 s -> `epoch 691 anchored on lan`; the T-Deck archived `t:observation f:X3SQS6 … ts:2026-10-23_23:54:29 epoch:691.71` |

## MeshCore: the same rules (2026-10-24)

The MeshCore bridge now has the Meshtastic bridge's gate and counters: heard
traffic crosses only under a clock and 20 s after boot (`no_clock`,
`settling`), old news is counted (`stale`), only the Regional room crosses
(`not_regional`), and each sender has four of the hour (`sender_capped`), on
`/api/status` `mc`. It needs no time prefix: a MeshCore channel message
carries the XPRS packet's own `ts:`, so its readers see when the words were
said. Verified on the host (`test_mc_host.sh`, cases 17-20) -- the bench has
no MeshCore node, and the T-Deck runs in `meshtastic` mode, so `mc` does not
appear on its status. Both boards reflashed with the build that carries it
(T-Deck `source:ntp`, `settling:1` at 40 s; C3 `source:ntp` at 9 s).
